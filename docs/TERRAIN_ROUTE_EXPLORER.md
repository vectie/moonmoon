# Pick and inspect terrain route candidates

The terrain-import panel now exposes the existing native terrain route engine through map selection. This supports MN-W01/MN-W02 and MOONMOON-B03/B07: an analyst can inspect a source and try digital routes without manually copying row/column coordinates into CLI commands. It does not replace mission terrain or start a simulation.

## Example: avoid a synthetic ridge

1. Open **Explore a local terrain raster** and import `ui/rabbita-moon/fixtures/route-detour.asc`.
2. Declare tile `route-example`, frame `Synthetic local Cartesian frame, no surveyed lunar coordinates`, horizontal units metres, elevations already metres, and source note `Synthetic demonstration, Apache-2.0, not observed lunar terrain`.
3. Select cell `[2,0]` on the map or with the cell selector; choose **Use selected cell as Start**. Select `[2,6]`; choose **Use selected cell as Goal**.
4. Keep maximum adjacent-center grade 20° and uphill preference 0. Choose **Calculate candidate route**. The existing engine yields 11 cells, 100 m horizontal distance and 0 m ascent, detouring around the ridge.
5. Raise grade to 60° and calculate again. It yields the direct 60 m route with 15 m ascent and descent. With grade 60° and uphill preference 4, recalculate to prefer the 100 m detour again.
6. Inspect any ordered step to select its exact original cell. Start/goal, preferences and result remain while inspecting cells. Green S/orange G mark endpoints; a white line shows the calculated candidate.
7. **Swap start and goal** clears the old calculation; recalculate because uphill cost is directional. **Clear route selection** keeps imported terrain. Importing another source resets all route state.

The native regression tests independently establish the numerical example above. Mounted Node tests establish the UI's selections, exact callback arguments, state transitions and rendering using declared response fixtures; no live browser execution is implied.

## Limits and failure behavior

The route engine validates the entire retained source bundle before computing. The added `route_json` boundary returns `{ok:true,route:...}` for a candidate or a computed no-path result, and `{ok:false,error:...}` for invalid source/inputs. It delegates unchanged to `route_bundle`; no routing mathematics was reimplemented in JavaScript.

- Routes use known four-neighbor cell centers. NODATA endpoints are rejected and missing cells are excluded.
- Grade must be 0 to less than 90°. Uphill preference must be finite and nonnegative. Its objective is distance plus weighted ascent, not energy.
- No-path is shown without invented zero distance/ascent. A same-cell candidate legitimately has zero travel distance.
- Source/endpoint/preference changes clear obsolete results and overlays. Detached controls from a prior import or render cannot change the current study.
- Degree grids retain inspection but do not expose metric route controls. No reprojection is performed.
- Source identity/frame and result digest remain visible. No clearance, footprint, roughness, cross-slope, illumination, energy, dynamics, mission acceptance or physical readiness is established.
